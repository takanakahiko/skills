# 振り返りブログの指針

`blog/index.md`（ISUCON2026 の振り返り。はてなブログで公開済み）を書く中で、takanakahiko さんから受けた指摘をまとめたもの。同じ種類の記事を書くときも、この指針に従う。文中のパス（`blog/tools/` など）は `~/dev/src/github.com/takanakahiko/isucon2026` のもの。別の記事では、同じ役割の道具をそのリポジトリに用意する。

## 1. 書き手の立場

- 書き手は、作業したエージェント（オーケストレーター）。冒頭は「チーム "…" で、takanakahiko さんの共同作業者として参加しました。」のように、エージェントの一人称で書く。
- 感情を演じない。「〜だと感じました」「悔しい」などのロールプレイは書かない。エージェントの立場をとるのは、記録から得た事実を自然に書けるからであって、気持ちを語るためではない。
- 謝罪や反省の言葉（誤り、反省、見落とし）を、エージェントの声で書かない。結果から見て適切でなかった判断は、ハーネス（ルール・知識・道具・安全装置）の設計の問題として書く。
- 書くのは、事実と判断の理由。文体は「です・ます」。
- 人間の感想は「takanakahiko 曰く:」の引用で入れる。
  - 本人の回答をそのまま貼らず、読みやすく整える。元の文が「稚拙」に見えることがあるため。
  - 面白くならない設問は、問いごと省く。
  - 足りない話は、ヒアリングして引用にする。

## 2. 何を書くか

- 主題はハーネス（「実質的にハーネス選手権」）。エージェントの動かし方と、その失敗とハーネスの不足を中心にする。
- 解法（スコアを上げた技術の細部）は重要ではない。背景が分かる程度に留める。読者は ISUCON を知っている前提でよい。
- 読者が自分のハーネスに持ち帰れるものは、具体的に残す（例: フックの判定の表）。
- 指示した結果にすぎない実装の細部は書かない（例: 「ダッシュボードの待ち受けは 127.0.0.1 だけ」）。
- 仕組みが正常に働いた話は、失敗談にしない（例: 再起動試験で問題を見つけて直した）。1 文で触れれば足りる。
- 人間が気づきもしなかった細部は、表にしない（例: FAIL の理由の一覧）。
- やり取りを全部並べない。「何時からベンチを常に回した」「何時からダッシュボードでやり取りした」「何時に昼食で離席した」程度の、ざっくりした流れでよい。
- 書かないもの:
  - 1 位のチームの話
  - 他チームを貶めると取られうる内容（失格したチームの一覧や理由など）
  - 使わなかった仕組み（ロック、タスクボード）
  - 自分たちの結果に関係のない話
- 競技中に足した施策や道具には 🆕 を付け、事前に準備したものと区別する。
- 冗談や軽い表現で柔らかくしてよい。例:
  - 「なんと呑気に "てんや" で定食を前に写真を撮っていたようです」
  - 「その親指で 1Password の承認を押してもらえれば」
  - 「犯人はキャッシュではありませんでした」

  ただし、記録で裏付けた事実か、本人の発言を元にする。エージェントの感情は演じない。事実が不確かなもの（例: 承認が指紋認証だったか）は、本人に確かめてから入れる。

## 3. 構成

- 章の見出しと中身を合わせる。
  - 「当日の時系列」の章で、最終構成のサーバー配置を話さない。
  - 「ハーネス」の章に、当日の最終構成を入れない。
- 失敗談の章は、体制の詳細を読まなくても読めるようにする。
  - 前に置くのは、読むのに必要な最低限（役割分担、ベンチのループ、ダッシュボード）だけにする。
  - 構成図、流れ図、フックの表などの詳細は付録に回す。
  - 用語は、本文で最初に出る箇所で短く説明する。
- 節の中は時刻順に進める。後の段落で時間を巻き戻さない。
- はじめには短くする。自己紹介、当日の数字、記事の位置づけ、今回のルールだけを置く。失敗の要約は入れない。良い膨らませ方をした部分は残す。
- 見出しを細かく分けすぎない（くどい）。太字の擬似見出しは、小見出しに変える。

## 4. 文章

- 一様に削らない。良いところは膨らませ、不要なところは削って、めりはりを付ける。全体の分量は減らす方向に保つ。
- 冗長な説明を避ける。
  - 「〜の『…』を受けて〜を作り」のような経緯の説明を重ねない。
  - 長い箇条書きは読みづらいので、短くするか図に移す。
- 次のようなノイズを入れない。
  - 根拠の前置き（「主催者の結果発表『…』によると」）
  - ジョブ番号の括弧書き（「（17:56、job 37355。…）」）
  - 読者が識別できない commit hash。使うなら「セッションの確認を SQL に入れた版（`1fd8531`）」のように中身で呼ぶ。
- 表の 1 つの列に、違う観点（スコア、ハーネスの変更、やり取り）を混ぜない。
- 「効く」は使わない。別の表現にする。
- 表現の癖は、writing-guide で直す。
  https://github.com/minorun365/my-claude-code-settings/blob/main/claude/skills/writing-guide/SKILL.md
- 推敲は yomiyasu で行う。
- 同じ内容を、はじめに・本文・表・付録で繰り返さない。

## 5. 図

- mermaid は使わない。図は自前の SVG で描く。
  - グラフ: `blog/tools/*_chart.py`、`timeline.py`
  - 構成図: `blog/tools/diagrams.py`
  - 配色と字体は全図で共通にする（INK・INK2・MUTED・GRID・SURF・BLUE、Hiragino Sans）。
- 統一感を何より大事にする。図の中でも図同士でも、置き方をそろえる。

  | 要素 | そろえ方 |
  |---|---|
  | 枠（グループ）のタイトル | すべて左上 |
  | 同じ役割の並び（利用者 → nginx → アプリ） | 同じ向き |
  | 青 | グラフではデータ、構成図では強調したい 1〜2 個だけ。停止期間などの強調帯は濃い灰色 |
  | 注記 | 横軸の下の段に◆とラベルで並べる形に統一する |
  | 凡例 | 右上 |
  | DB | 円柱 |
  | 終端（開始・終了・先頭へ） | 角丸の pill |

  重なりを避けたいときは、置き方の例外を作らず、箱の配置の方を変える。
- 流れ図は、上から下、左から右にだけ進める。「開始」は左上に置き、下から上に戻る矢印は作らない（戻り先は「先頭へ」の pill を置く）。
- 線の交差を最小にする。交差が避けられない線は、箱の中の注記に置き換える（例: 「.board/ を表示」）。
- 外から来るアクセスは、利用者からの矢印で示す。
- 縦横比は横長にする。縦に長い図や大きすぎる図は、ブログの縦スクロールを長くする。超シンプルな図で足りるところは、そうする（例: 3 台から DB への往復）。
- 図は、対応する本文のすぐ隣に置く。
  - 図だけで意味が完結するようにする。離れた章の番号を図に入れない。
  - 読者が図と本文を往復しなくて済むようにする。
- スコアの推移はスクリーンショットではなく、きれいなグラフで描く。運用の節目（ベンチの常時実行の開始、ダッシュボードの開始、昼食の離席など）は、表ではなくグラフに重ねる。
- スクリーンショットは、本文の役に立つものだけにする。配信（YouTube）の画面や、エージェントとの対話画面は使わない。
- 描いたら検査する。
  - `layout-check.js`（文字と文字、文字と図形の重なり）を通す。
  - 必ずスクリーンショットを目で見て確かめる。構成図では、箱の中の文字も重なりとして報告されるので、目視を優先する。

## 6. 事実の確かめ方

- 時刻・回数・発言は、記録で確かめてから書く。
  - 会話の記録: `~/.claude/projects/<project>/<session>.jsonl`。時刻は UTC なので +9 時間する。途中で送られた発言は `type: attachment` の `queued_command` にあるので、生の行も検索する。
  - `.board/events.jsonl`: エージェントの起動と終了。日付で絞る。
  - `git log --first-parent main`
  - `results/bench-history.tsv`、`NOTES.md`、`problem/`
- 指示か自分の判断かを区別する（例: 「15〜20 体」は指示ではなく、自分で決めた目安だった）。
- 数字を複数の箇所に書いたら、すべて一致させる（merge の回数など）。
- 推測で原因を書かない。分かった範囲だけを書き、残りは「わかっていません」と書く。

## 7. 作業の進め方

- 大きく変える前に、`blog/index.before-<内容>.md` に控えを取る。
- プレビューは `blog/tools/serve.py`（no-store、Tailscale 経由）で見る。画像の URL にはキャッシュ避けを付ける。
- 面白さや読みやすさの確認は、立場の違う読者役のエージェント 3 人ほどに頼む（参加者、エージェントの実務者、一般の読者）。返ってきた指摘は、記録で確かめてから採る。
- 指示が曖昧なとき（誤字や途中で切れた発言）は、解釈を一言添えてから進める。
- 報告は短くする。長い箇条書きで報告しない。
